# 外部画像キャッシュ戦略

## 問題

アニメのカバー画像は外部サイト（`m.media-amazon.com`, `images.prod.hjholdings.tv` 等）から配信している。
これらの画像はブラウザの **memory cache** にしか保持されず、タブを閉じたりデプロイで再読み込みすると再取得が走る。

外部サーバーは適切な `Cache-Control: max-age=604800, public` を返しているが、クロスオリジン画像はブラウザが disk cache に入れないケースがある。

---

## 解決策の比較

### 1. Worker 画像プロキシ

Worker に `/api/img?url=...` エンドポイントを追加し、外部画像を fetch して Cache API でキャッシュ。フロントエンドは自ドメイン経由で画像を読み込む。

| 項目 | 内容 |
|------|------|
| 実装コスト | 低（40行程度 + `getCleanImageUrl` 変更） |
| キャッシュ永続性 | 高。CDN エッジキャッシュ + ブラウザ disk cache の両方が効く。デプロイ・タブ閉じに耐える |
| コスト | Workers Free: 100K req/日。個人利用なら十分 |
| レイテンシ | 初回: +50-200ms（Worker → origin）。以降: エッジから sub-10ms |
| メリット | 同一オリジンになるため disk cache が確実に効く。CORS 問題も解消。既存の `run_worker_first = ["/api/*"]` がそのまま使える |
| デメリット | キャッシュミス時に Worker CPU を消費。オープンリレー防止のためドメイン許可リストが必要 |
| 著作権リスク | 低。ブラウザの fetch と機能的に同等。CDN キャッシュは一時的 |

### 2. Service Worker（PWA）

Service Worker を登録し、外部画像ドメインへの fetch をインターセプトして Cache Storage に保存。

| 項目 | 内容 |
|------|------|
| 実装コスト | 中（Service Worker 登録 + キャッシュ戦略の実装。Workbox 等のライブラリ利用も検討） |
| キャッシュ永続性 | Chrome/Firefox: 高。Safari: やや不安定（7日間未使用で evict される場合あり） |
| コスト | サーバーコストなし |
| レイテンシ | cache-first なら2回目以降は即座。初回は現状と同じ |
| メリット | サーバー変更不要。オフライン対応も可能 |
| デメリット | CORS ヘッダーがない外部画像は opaque response になり、1件あたり約7MB のクォータを消費。Safari のキャッシュ eviction が不安定。デバッグが困難 |
| 著作権リスク | なし。ブラウザのキャッシュと同等 |

### 3. Cloudflare R2

画像を R2 バケットにダウンロード保存し、自ドメインから配信。

| 項目 | 内容 |
|------|------|
| 実装コスト | 高（R2 バインディング、同期パイプラインでの画像DL、DB の URL 管理、既存画像の backfill） |
| コスト | Free: 10GB / 10M read req/月。カバー画像なら数万枚は余裕 |
| メリット | 外部サイトの障害・URL変更に影響されない。完全な可用性 |
| デメリット | 実装が重い。画像更新の追従が必要。moving parts が多い |
| 著作権リスク | 最も高い。第三者の画像を自インフラに複製・配信することになる。個人利用なら実質的リスクは低いが、技術的には再配布 |

> **注意:** R2 はキャッシュではなくストレージ。リクエストは毎回発生するため、クライアント側キャッシュ（disk cache / Cache Storage）より遅い。R2 の価値は「外部サイトが画像を消した・URLを変更した場合の保険」であり、キャッシュ高速化の手段ではない。

### 4. Cloudflare Cache Rules

Cloudflare ダッシュボードでプロキシエンドポイントのキャッシュ TTL を設定。

| 項目 | 内容 |
|------|------|
| 実装コスト | 最低（ダッシュボード設定のみ） |
| キャッシュ永続性 | 方式1と同等 |
| 前提条件 | **方式1（Worker プロキシ）が必須**。外部オリジンへの直接リクエストは自ゾーンを通らないため Cache Rules は適用できない |
| メリット | コード変更なしで TTL をチューニング可能 |
| デメリット | 単独では機能しない。Free プランではルール数に制限あり |

### 5. ブラウザヒント（preload / fetchpriority）

`<link rel="preload">` や `fetchpriority="high"` で画像読み込みを最適化。

| 項目 | 内容 |
|------|------|
| 実装コスト | 低 |
| キャッシュ永続性 | **なし。キャッシュ問題は解決しない** |
| メリット | ファーストビューの表示速度を改善できる可能性 |
| デメリット | SPA ではルートロード後にしか画像 URL が確定しないため preload の効果が薄い |

---

## 推奨

### 最小構成: 方式1（Worker 画像プロキシ）

最もシンプルに問題を解決できる。

1. `/api/img` Hono ルートを追加
2. 許可ドメインを allowlist（`m.media-amazon.com`, `images.prod.hjholdings.tv`）
3. Cache API で 7日間キャッシュ + `Cache-Control: public, max-age=604800` を返却
4. `getCleanImageUrl()` を `/api/img?url=<encoded>` 形式に変更

### 拡張構成: 方式1 + 方式2（Worker プロキシ + Service Worker）

- 方式1 で同一オリジン化 + CDN エッジキャッシュ
- 方式2 でクライアント側の永続キャッシュ + オフライン対応
- 画像が自ドメイン経由になるため、Service Worker で CORS / opaque response の問題が発生しない

方式3（R2）はキャッシュではなくストレージ。外部サイトの画像消失に備えるアーカイブ用途であり、キャッシュ高速化の目的では不要。
